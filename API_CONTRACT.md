# API Contract — «Умный планировщик задач»

---

## 1. Схема данных: Task

| Поле          | Тип                                   | Обязательность | Описание                                  |
|---------------|----------------------------------------|-----------------|--------------------------------------------|
| `id`          | `UUID` (string, формат UUID4)          | генерируется сервером | Уникальный идентификатор задачи |
| `title`       | `string`                               | обязательное    | Заголовок задачи                          |
| `description` | `string`                               | обязательное    | Подробное описание задачи                 |
| `status`      | `enum`: `new`, `in_progress`, `done`   | обязательное, по умолчанию `new` | Текущий статус задачи |
| `created_at`  | `string` (ISO 8601, с таймзоной, UTC)  | генерируется сервером | Момент создания задачи |

Пример полного объекта `Task`:

```json
{
  "id": "3fa85f64-5717-4562-b3fc-2c963f66afa6",
  "title": "Купить билеты",
  "description": "На конференцию в Берлин",
  "status": "new",
  "created_at": "2026-09-19T10:15:30+00:00"
}
```

**Важно:** тип `id` — строго `UUID`, а не числовой инкремент. Это решение
зафиксировано командой во избежание конфликта типов между сервисами.

## 2. Endpoint 1 — Task Service: создание задачи

```
POST /api/tasks
Content-Type: application/json
```

### Тело запроса

Без `id` и `created_at` — эти поля генерирует сервер. Поле `status` в запросе
не передаётся — сервер всегда выставляет `new` по умолчанию.

```json
{
  "title": "Купить билеты",
  "description": "На конференцию в Берлин"
}
```

| Поле          | Тип      | Обязательность |
|---------------|----------|-----------------|
| `title`       | `string` | обязательное    |
| `description` | `string` | обязательное    |

### Успешный ответ

```
HTTP 201 Created
Content-Type: application/json
```

```json
{
  "id": "3fa85f64-5717-4562-b3fc-2c963f66afa6",
  "title": "Купить билеты",
  "description": "На конференцию в Берлин",
  "status": "new",
  "created_at": "2026-09-19T10:15:30+00:00"
}
```

### Ошибки

| Код | Условие                                  |
|-----|-------------------------------------------|
| 422 | Не передано обязательное поле (`title`/`description`) или неверный тип |

## 3. Endpoint 2 — Notification Service: приём события о создании задачи

```
POST /api/webhooks/task_created
Content-Type: application/json
```

### Тело запроса

Полный объект `Task`, каким он был только что создан в Task Service
(см. раздел 1 и раздел 4).

### Успешный ответ

```
HTTP 200 OK
Content-Type: application/json
```

```json
{
  "status": "ok"
}
```

### Ошибки

| Код | Условие                                             |
|-----|-------------------------------------------------------|
| 422 | Тело запроса не соответствует схеме `Task` (например, `status` вне enum, отсутствует `id`) |
| 500 | Внутренняя ошибка обработки на стороне Notification Service |

## 4. Формат сообщения вебхука (Task Service → Notification Service)

После **успешного** сохранения задачи в БД (после `commit`), Task Service
синхронно вызывает Notification Service:

```
POST http://<notification-service-host>:8001/api/webhooks/task_created
Content-Type: application/json
```

Тело запроса — **тот же самый объект**, что был только что возвращён клиенту
из `POST /api/tasks` (со всеми пятью полями, включая `id` и `created_at`):

```json
{
  "id": "3fa85f64-5717-4562-b3fc-2c963f66afa6",
  "title": "Купить билеты",
  "description": "На конференцию в Берлин",
  "status": "new",
  "created_at": "2026-09-19T10:15:30+00:00"
}
```

Никаких дополнительных полей (например, `event_type`, `timestamp` события,
`source`) в рамках лабораторной работы не передаётся — тело вебхука
дословно совпадает со схемой `Task`.

### Обработка ошибок доставки (со стороны Task Service)

Если Notification Service недоступен или возвращает ошибку — Task Service:
1. **не падает** и не возвращает клиенту ошибку по `POST /api/tasks`
   (задача уже успешно сохранена в БД, это отдельная гарантия);
2. логирует неудачу;
3. кладёт задачу во внутреннюю очередь в памяти и повторяет попытку
   доставки с фиксированным интервалом, максимум 5 попыток.

## 5. Ветки и рабочий процесс

- Общая ветка разработки: `dev`
- Ветка Task Service: `feature/tasks-service`, создаётся от `dev`
- Ветка Notification Service: `feature/notifications-service`, создаётся от `dev`
- Изменения в `main` — только через Pull Request с ревью Tech Lead'а
- Любое изменение данного файла (`API_CONTRACT.md`) в отдельной ветке
  должно быть анонсировано команде **до** открытия PR, чтобы избежать
  конфликтов слияния в структуре общих типов данных
